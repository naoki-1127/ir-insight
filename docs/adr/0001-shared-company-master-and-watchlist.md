# ADR 0001: 共有の銘柄マスタとユーザごとのウォッチリスト

- ステータス：採択
- 日付：2026-11-18

## 背景

現状の `Company` は、全員に共通の「登録済み銘柄」として使われている。ユーザごとに銘柄を管理できるようにするにあたって、銘柄の持ち方を次のどちらにするかを決める必要がある。

1. **ユーザごとに銘柄を持つ**：`Company` に `userId` を付ける
2. **銘柄マスタを共有し、ユーザとは `Watchlist` で紐づける**

なお、本アプリは個人向けとして設計し、テナント（組織）の層は設けない。データの分離単位はユーザとする。

検討で前提にした事実は次のとおり。

- 8-K、決算の数値、AI による要約は、いずれも EDGAR 由来の公開情報であり、誰が見ても中身は同じ
- ユーザごとに違うのは「どの銘柄を追いかけているか」だけ
- コストと制約は銘柄単位で発生する（OpenAI の要約費用、SEC EDGAR の 10 req/s 未満という制限）
- マスタに EDGAR の全企業をあらかじめ入れておくことはしない。使われない銘柄はマスタに置きたくない

## 決定

**銘柄マスタ（`Company`）を共有し、ユーザとは `Watchlist` で紐づける。マスタへの追加は、誰かが銘柄を登録した時点で行う（遅延登録）。**

### データの区分

| テーブル | 区分 |
|---|---|
| `Company`、`Document`、`DocumentContent`、`Financial` | 共有データ（EDGAR 由来） |
| `Watchlist` | ユーザデータ（`userId`） |

```prisma
model Watchlist {
  id         String    @id @default(uuid())
  userId     String
  companyId  String
  archivedAt DateTime?          // アーカイブ中なら日時が入る
  createdAt  DateTime  @default(now())
  user       User      @relation(fields: [userId], references: [id], onDelete: Cascade)
  company    Company   @relation(fields: [companyId], references: [id])
  @@unique([userId, companyId])
  @@index([companyId])
}
```

### 登録の流れ（`POST /api/companies`、MCP の `register_company`）

ユーザは引数で受け取らず、認証結果から決める。

1. ticker を EDGAR の企業一覧（`company_tickers.json`）で解決し、CIK と社名を得る。見つからなければ 404 にし、マスタには何も入れない
2. `Company` を `cik` で探し、なければ作成する
3. `Watchlist` に `(userId, companyId)` を upsert する。アーカイブ中であれば復元する
4. 新しくマスタに入った銘柄であれば、初回取得ジョブを BullMQ に投入する

2 と 3 は 1 つのトランザクションで行う。`cik` は一意制約があるため、同時に登録されても重複しない。
既にマスタにある銘柄の場合はウォッチを追加するだけで、EDGAR へのアクセスも要約も発生しない。

### アーカイブとウォッチされなくなった銘柄

- 既存の「アーカイブ（論理削除と復元）」機能は、`Company.deletedAt` から `Watchlist.archivedAt` に移し、ユーザごとに働くようにする
- `Company` は削除しない
- 日次の `check-all` は「アーカイブされていないウォッチが 1 件以上ある銘柄」だけを対象にする。誰も追いかけていない銘柄の取得と要約は行わない
- 取得済みの `Document` と `Financial` は残す。再登録されたときに要約をやり直さずに済む
- マスタを小さく保つ必要が出てきたら、「N 日間ウォッチされていない銘柄を削除する」バッチを後から追加する（今回は作らない）

### 共有マスタを守るためのルール

マスタは全ユーザで共有するため、登録は「どのユーザからでも共有データに書き込める操作」になる。そこで次のルールを設ける。

- EDGAR に実在する銘柄だけを受け付ける
- `Company` の列（CIK、社名、ticker、市場）は EDGAR から得た値だけで埋め、利用者の入力は使わない。互換性のために `cik` と `name` をリクエストで受け取ることはあるが、使わない
- 登録にはユーザ単位のレート制限をかける（今後）
- `Company` の更新（社名やティッカーの変更への追従）と、`Document`、`DocumentContent`、`Financial` への書き込みは、ワーカーとバッチだけが行う

### 現行スキーマからの変更点

- `Document.userId` を削除する（文書は共有データであり、ユーザとは関係しない）
- `Company.deletedAt` を削除し、`Watchlist.archivedAt` に移す
- `Company.ticker` の `@unique` を外し、インデックスだけにする。ティッカーは変更や再利用があるため、銘柄の識別子は `cik` とする
- 既存の `Company` は、移行時に既存の全ユーザの `Watchlist` に入れる。`deletedAt` は `archivedAt` として引き継ぐ

### MCP の共有キーの扱い（暫定）

MCP サーバは現在、ユーザを持たない共有キー（`MCP_API_KEY`）で backend を呼んでいる。ウォッチはユーザごとなので、共有キーでの呼び出しは `MCP_API_KEY_USER_ID` のユーザとして扱う。`MCP_API_KEY` が設定されていて `MCP_API_KEY_USER_ID` がない場合、backend は起動時に終了する。
ユーザごとの API キーと内部 API に置き換えた時点で、この暫定措置は廃止する。

## 検討した他の案

### 案 1：ユーザごとに銘柄を持つ

採用しない。理由は次のとおり。

- 同じ決算をユーザの数だけ取得・要約することになり、OpenAI の費用と EDGAR へのリクエストがユーザ数に比例して増える
- `Document` と `Financial` もユーザごとに分ける必要があり、分離しなければならない範囲が広がる
- 同じ企業のレコードがユーザごとに重複し、一意制約が `(userId, cik)` になる

### EDGAR の全企業をマスタにあらかじめ入れておく

採用しない。マスタが使われない銘柄で埋まるうえ、企業一覧に追従する同期処理が必要になるため。遅延登録であれば、マスタには誰かがウォッチしたことのある銘柄だけが入る。

## 影響

- 良い点
  - 取得と要約は銘柄ごとに 1 回で済み、費用と EDGAR へのリクエストがユーザ数に比例しない
  - ユーザごとの分離が必要なのは `Watchlist` などのユーザデータだけで、保証すべき範囲が狭い
- 注意する点
  - 共有マスタなので、ユーザは自分がウォッチしていない銘柄の決算も ID を指定すれば参照できる（`/ir/detail/:documentId` など）。公開情報なので問題とはしないが、表示範囲を「自分のウォッチ銘柄だけ」に絞るかは別途決める
  - 「ある銘柄がマスタに存在する＝誰かがウォッチしたことがある」ことは推測できる。公開情報の銘柄名だけなので許容する
